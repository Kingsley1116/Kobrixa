# E1 USB connection recovery — bounded contract proposal

Status: controller-approved implementation contract, 2026-10-26. This freezes the proposed names and semantics for the unpublished API 1.8 batch; it does not claim implementation or acceptance. Worker/import files are outside this contract write set. H-P is assigned protocol/SDK/resource schemas; controller owns broker/host composition and generic renderer handoff.

## Decision

Add **one read method**, **one topic/event on the existing common event bus**, and **one v2 declarative trusted core action** in the current unpublished API 1.8 batch:

- `devices/connectionRecovery/read`, params `{}`.
- Existing `devices/subscribe` gains `{topic:"connectionRecovery"}`; event `devices.connectionRecovery`; existing ACK/unsubscribe/resync machinery, with catchup through this read method and fresh subscription snapshots (there is no public `events/snapshot` method today).
- V2 action `{kind:"core", action:"cancelConnectionRecovery", recovery:{scope:"data",key:LocalId}}`.

Do NOT publish a plugin cancel/reconnect method, add a device cancellation permission, reuse journal fault IDs, or let plugin metadata establish recovery identity. The host action consumes a fresh CoreActionReference from the existing core ledger. A new process can observe the current recovery without owning the old connection and without starting discovery/connect.

This cannot be only a lifecycle-event adapter: the broker needs a retained snapshot and an exact attempt cancellation/publication fence.

## Actual baseline and legacy parity

- `main/device-broker/broker.ts:71–99,343–455`: BrokerLifecycleEvent is main-only/transient. `lostUsb` owns retry timers, original principal/provider generation, serial digest, loss policy, attempt count and original quiescence promise. There is no public retained connection-recovery snapshot or token.
- The broker schedules only USB with non-null serial identity and enabled auto reconnect. Fixed intervals are 1000/2000/5000/10000 ms; backoff is 1000,2000,5000 then 5000. Limits are 3/5/10 or unlimited. Current committed policy is checked on subsequent steps; loss policy also gates eligibility. Do not clamp unlimited to an arbitrary new finite count.
- `broker.ts:2024–2100`: reconnect waits original cleanup, checks original principal/provider generation, discovers exactly one matching USB serial identity and checks journal identity evidence. It creates a NEW session; it does not replay motion/program/upload/recording. Preserve those checks, and the authority/provider/source policy checks that already guard connection work.
- `legacy-device.ts:245–293`: translates waiting/connecting/restored/cancelled/unavailable/exhausted for a previously observed descriptor. Restored currently carries deployment `none`; it does not certify that a previous upload survived.
- `renderer/execution/execution.ts:184–225,565–640`: waiting/connecting clears the old active session; exhausted maps to retry-exhausted, unavailable to manual-required. Restored accepts only the matching old session/recovery; deployment is retained only on matching verified build evidence, otherwise prior deployment produces upload-required. Cancel currently calls Disconnect on the old recovery session, suppresses restored while pending, retains recovery/error on failure, and prevents replacement Connect until cancellation succeeds.
- Preserve this user-visible behavior, but do not copy the old-session Disconnect implementation into the new public contract. It can no longer identify a newly adopted recovery connection reliably. The new host target must identify the recovery attempt itself.
- `ui-bridge.ts`/`plugins/controller.ts` already re-resolve original resource/binding/state for core actions, and `plugins/core-recovery.ts` supplies a 5-second, single-claim, exact-target CoreActionLedger. `ui-interactions.ts` has independent core control slots bypassing ordinary form/command queue admission. Extend these seams.

## Exact proposed wire types

Use existing Handle (canonical lowercase UUIDv4), Counter (safe nonnegative integer), namespaced provider ID and BusinessResult/DeviceFailureDetail conventions. Every object/variant is strict; no additional fields.

```ts
type ConnectionRecoveryRef = {
  recoveryId: Handle; // generated by host once per loss/recovery episode
  providerId: string;
  providerGeneration: Counter;
  previousSessionId: Handle;
};
type ConnectionRecoveryBase = ConnectionRecoveryRef & {
  name: string; // 1..200 code points, <=800 UTF-8 bytes, single line
  attemptsStarted: Counter; // discovery/reconnect attempts begun, not successful connects
  retryLimit: 3 | 5 | 10 | "unlimited";
};
type ConnectionRecovery = ConnectionRecoveryBase &
  (
    | { phase: "waiting"; retryAfterMs: number } // integer 0..10000, display hint only
    | { phase: "connecting" }
    | { phase: "cancelling" }
    | { phase: "cancel-failed"; error: ConnectionRecoveryError }
    | {
        phase: "cancelled";
        reason:
          "user" | "policy" | "authority-lost" | "provider-retired" | "superseded" | "shutdown";
      }
    | { phase: "retry-exhausted" }
    | {
        phase: "manual-required";
        reason:
          | "auto-disabled"
          | "identity-unavailable"
          | "identity-ambiguous"
          | "authority-unavailable"
          | "provider-unavailable"
          | "cleanup-required";
      }
    | { phase: "restored"; sessionId: Handle }
  );
type ConnectionRecoveryError = {
  reason: "cleanup-pending" | "cleanup-failed";
  message: string; // sanitized single line, 1..256 code points / <=1024 bytes
};
type ConnectionRecoverySnapshot = {
  hostEpoch: Handle;
  revision: Counter; // host-wide projection revision, never reset within epoch
  recovery: ConnectionRecovery | null;
};
// devices/connectionRecovery/read
// params: {}; result: BusinessResult<ConnectionRecoverySnapshot, DeviceFailureDetail>
// devices/subscribe {topic:"connectionRecovery"}
// result: existing {subscriptionId,sequence,snapshot:ConnectionRecoverySnapshot}
// events/deliver: existing envelope, kind="devices.connectionRecovery",
// delivery="control", data=ConnectionRecoverySnapshot
```

Limits and semantics:

- One current/latest episode globally, matching the broker's one-session limit. Retain the latest terminal episode until a new episode or a successful unrelated explicit connection supersedes it; no unbounded history, journal record or timer per observer. On supersession retire the old attempt synchronously; a projection with `recovery:null` is revisioned. Host restart starts a new hostEpoch with null and does not restart recovery from this data.
- Full serialized snapshot <=4096 UTF-8 bytes, validated structurally and semantically before publication. Existing common limits remain unchanged: 32 active subscriptions/source, 256/host, <=65536 bytes/event, existing seven queued control-event overflow threshold and ten-second pending ACK handling; the topic consumes ordinary quota, not a separate pool. Do not emit countdown ticks: publish transitions/policy changes; retryAfterMs is a host-computed monotonic remaining-time hint at snapshot creation. Decreasing the hint alone does not increment revision.
- `restored.sessionId !== previousSessionId`, original provider/generation must match the restored session at publication. Finite retryLimit/exhausted cross-fields must be consistent; attemptsStarted advances exactly on original attempt admission. Overflow must retire rather than wrap counters. `cancel-failed` keeps scheduling revoked and refers only to original cleanup, never authorizes another reconnect.
- Do not expose serial digest, USB/HID path, native descriptor, authority references, original plugin owner, action tokens, provider implementation details or deployment/file paths.
- A no-episode read returns null. Disabled/safe/unavailable provider observation does not register/start a provider or read optional preference storage just to make a response. Existing devices.read permission and current channel owner checks apply; projection read must not call getSession to acquire session ownership.

The extra cancelling/cancel-failed states preserve legacy pending/failure behavior rather than treating requested cancellation as completed cleanup. Terminal notice names deliberately match the new UI meaning; legacy main-only translation can continue mapping to its existing event names.

## Event catchup, versions and SDKs

Add a distinct 1.8 device schema/dispatch extension; keep the old device schemas/definitions available for 1.5–1.7 sessions. The new standalone method, subscribe topic, subscribe-result snapshot alternative and event variant are admitted only after a successful validated initialize offer/reply intersection >=1.8 and existing devices negotiation. Incoming remote initialize params alone cannot widen support. Failed/abandoned initialization and channel retirement erase eligibility. No UI v2 readiness requirement for a pure device observer; only the declarative action resource requires UI v2.

Do not silently widen the old global devices/subscribe result union or old event parser. Current RpcPeer only has explicit UI version dispatch, so H-P must add the analogous effective-initialized-version selection for this device extension, and the host attachment must select its event schema consistently. Keep `devicesContractVersion:1` and event envelope version 1; API 1.8 gates the additive topic/method. Older peers receive neither the new topic nor the new event. No extra public minor bump or release claim.

Producer takes its initial snapshot and installs the subscription in one synchronous broker turn; activate only in the existing afterReply hook, abandon on failed reply. All changes enter CommonEventLedger. Initial snapshot plus ordered events has no read/listen gap. Catchup uses the read method's authoritative projection revision, or a new subscribe response with its existing sequence-zero buffered activation boundary. The common ledger has an internal snapshot helper, but no new public snapshot RPC is needed. The consumer compares hostEpoch/revision so a delayed read cannot replace a newer event and a delayed event cannot replace a newer read; sequence ACK ownership remains with the existing inbox. Business terminal phases do not terminal-close this topic: the observer must see the next episode. Transport terminal/resyncRequired closes the affected stream as usual; observer drops the old subscription, waits cleanup and explicitly establishes a fresh read/subscription. Never resume a terminal stream or restart connection work during catchup.

JS: `ctx.devices.connectionRecovery.read({}, signal?)`; Python: `await ctx.devices.connection_recovery.read({})`, five-second timeout, one call/no automatic retry, standard AbortSignal/asyncio cancellation and abandoned reply handling. Both `devices.subscribe({topic:"connectionRecovery"}, listener)` implementations need an explicit refresh branch (their present fallback assumes authority/context). Read-only recovery attachment must not invoke discover/connect or acquire an original session user. Typed snapshot/result correlation must match the originating topic; reject malformed fields, extra fields and wrong snapshot kinds. Use existing shared event inbox, not a feature bus.

## Trusted cancel action and host seam

Resource action (v2 panel action node; also legal in v2 status action list):

```ts
{kind:"core", action:"cancelConnectionRecovery",
 recovery:{scope:"data",key:"connection-recovery-id"}}
```

The referenced declared scalar is nullable string, maxLength 36, initial null or valid Handle, same opaque-slot discipline as recording stop. The plugin may copy the public recoveryId into this slot but the slot confers NO authority. No controller-supplied provider/session/owner/actionRef arguments. No new public RPC, command origin or preload endpoint: use existing bridge `interact({kind:"core",binding,actionId})`/panel core invoke routing and return existing control-accepted/error shape.

Host re-resolves the original registered v2 resource, current owner/process, full binding/scope, current presentation and visible UI site; reads the slot; looks up exact live recoveryId and captured provider generation. Action admission ignores ordinary form validation, feature enabledWhen and command queue; a stale/hidden/retired binding still rejects. Use an independent one-inflight core slot per binding/action, separate from Open/StopRecording. A feature must have devices.read and a validated declaration to expose this action; it does not need devices.connect/control, does not impersonate the original plugin, and cancellation does not acquire collaboration holder authority. Only the trusted workbench interaction path mints the core token.

Extend host-only CoreActionTarget with:

```ts
{kind:"device-connection-recovery-cancel"} & ConnectionRecoveryRef
```

CoreActionReference.scope already binds hostEpoch/workbench. Extend DeviceBrokerPort with a host-only port, keeping journal `recovery` separate:

```ts
connectionRecovery: {
  snapshot(): ConnectionRecoverySnapshot; // trusted internal read, no I/O
  cancel(input: {
    target:ConnectionRecoveryRef;
    action:CoreActionReference;
  }): Promise<BusinessResult<ConnectionRecoverySnapshot, DeviceFailureDetail>>;
}
```

One current, unused ledger claim must match all target fields before any mutation. Stale/foreign/terminal targets return existing PLUGIN_E_STALE_RESOURCE with resource/rpc detail; absent/replayed/expired core claim returns existing permission/user-action-required. Do not add a new public recovery resource error enum just for this seam. Already-running original cancellation may be joined only by the exact retained host operation; a new explicit action after cancel-failed retries original cleanup only. Token completion is in finally; original operation/deadline tracking must not depend on keeping an unclaimed five-second token alive.

Cancellation algorithm requirements:

1. Atomically claim exact target and mark that episode cancelled-for-continuation before first await; clear its retry timer, increment/retire its continuation generation and abort its own attempt controller. Publish cancelling. No reconnect, rediscovery, new session, stop-current, or preference toggle to perform Cancel.
2. Thread this internal attempt fence through discovery, journal load, candidate handoff, provider.connect, sources initialization and final session adoption/publication. Existing code checks lostUsb after discovery but does not make lostUsb membership part of every connect/source continuation and restored publication. Merely calling forgetUsb would be insufficient.
3. If cancellation wins before final adoption, late provider success must not publish a usable session/restored event. Settle/close only the connection acquired by that exact attempt, through existing provider cleanup/lane handling with its original provider generation and deadlines. Do not overwrite session or disconnect/stop whichever session is current. Do not release an occupied lane while original I/O remains unresolved. Carry original cleanup failure as cancel-failed/quarantine/blocker; never report completed cancellation while orphan cleanup is unknown.
4. If restored adoption wins atomically first, Cancel is stale; it must not disconnect that now-current new session. User can separately choose ordinary Disconnect. Suppress any older restored callback after cancellation/supersession/provider replacement, both host-side and via consumer epoch/revision fences.
5. Existing loss stop/readback/drain/journal work continues independently; Cancel only stops automatic connection attempts. It does not mark original motion safe, finalize recordings, clear faults or extend any drain window. Successful cancellation means original retry work is retired/settled, not that the physical device is confirmed stopped.
6. A replacement explicit Connect must not race a cancelling attempt. Use existing connection lane/admission; wait for clean retirement or return busy. After a new explicit connection is admitted, old recovery cannot restore over it. Provider disable/replacement, authority loss, shutdown and policy auto-off likewise retire the exact episode and late callbacks. Provider re-enable never resurrects its old identity.

## USB recovery is not journal stop recovery

`DeviceRecoveryPort`/`recovery-port.ts` manages persisted safety faults, identity-confirmed observeIdle/stop and journal resolve. It can retain unconfirmed evidence across host restart and requires matching current physical identity or explicit user confirmation. Keep its interface/actions separate. A successful new USB connection does not prove brake/readback or journal durability, and cancelling connection retry never clears its faults. Cold/headless observation cannot connect to obtain proof. An unrelated device must remain untouched.

Deployment/pending Run remain core: preserve legacy lifecycle translation or add a trusted projection adapter to core execution so matching restored sessions undergo its existing build/deployment verification. Public restored only names a new session; the plugin cannot set verified/buildId or restore a pending Run. When old deployment is not verified, core continues showing upload-required. Panel/process reload can display current recovery/notice, never regenerate pending Run or replay upload/motion/recording.

## Required focused acceptance cases

1. Schema/semantic shared JS/Python cases: every phase, strict extra-field rejection, invalid UUID/provider generation, name/error byte bounds, 4096-byte boundary, illegal restored old-session id, wrong snapshot topic, finite retry-limit consistency, old-session version rejection and no old-event widening.
2. Fake-clock policy: 1/2/5-second backoff, all fixed intervals, 3/5/10/unlimited, current committed changes only affect subsequent legal steps; no extended original attempt/deadline. Missing/duplicate/changed serial, journal mismatch, Wi-Fi loss => correct manual/error policy, never fallback address/name matching.
3. Snapshot/subscribe race and buffered afterReply; ACK/resync, terminal overflow, owner/channel retirement, fresh observer after process restart sees retained phase/notice without discover/connect/provider activation. Read and subscription work independently of UI v2 negotiation.
4. Trusted action: genuine current panel/status binding, exact original resource/slot; malformed/stale/replayed token, wrong workbench/owner/provider generation/recoveryId, hidden/closed/replaced view all denied without I/O. Invalid form must not trap Cancel. Shared ledger token count returns to baseline.
5. Barrier races: cancel while waiting, during original cleanup wait, discover, journal load, provider connect, sources initialization and just before adoption. No late restored/no leaked connection; only original connection cleanup. Restored-before-cancel returns stale and does not disconnect the new session. Unrelated manual connection/provider replacement stays untouched.
6. Cleanup failure/deadline: visible cancel-failed with original handle; explicit retry joins original cleanup, no timer restart/new deadline/fake success. Process observer crash does not cancel healthy provider-owned recovery; original connection principal retirement follows existing broker policy, never adopts the new observer as retry principal.
7. Legacy parity: waiting/connecting/cancel/error restoration/exhausted/manual-required, stale restored suppressed, no implicit pending-run, core upload-required when deployment is not verified. Original loss recording drain and journal-unconfirmed evidence survive recovery cancellation.
8. Actual in-memory RpcPeer/JS and Python stdio read + common-event catchup + trusted host cancel action against real broker/fake provider, including negative ownership/version cases. Native/hardware USB unplug/retry/cancel remains a later declared gate, not replaced by these tests.

No tests run for this architecture-only task. Source inspection establishes the seam and required changes, not implementation readiness.
